# Alpha 33 stability deep dive — Pixel 8 + Glass Alpha 16

**Scope and evidence.** This is a postmortem of the physical run `exp-20260925-172945-e6d8` and the independent USB mirror checks on 2026-09-25. It uses the [test report](ALPHA33_LAB_TEST_REPORT.md), trial JSONL, run trace `ai-e589bc9b-1427-43b5-8bed-f1656bc9351e`, Android/Gateway/Glass source, and focused local tests. One Pixel and one PC cannot establish reliability for every phone, app, or network. Items below distinguish confirmed defects, strong code-path findings, and work that still needs measurement.

## What the run actually proved

The only scored mission, “Turn on auto-rotate,” failed: the phone-side probe still read `accelerometer_rotation=0` after 47 model turns and 392.7 seconds. Its trace records 46 tool actions, 8 tool errors, 22 observed screen changes, no provider retries or rate limits, and repeated navigation away from the intended Display setting. The next three missions never started because `lab.start` returned `HUMAN_HAS_CONTROL`; the canary halted at 4/8 attempts. There was no A/B comparison and the delete-file approval test did not run.

The USB media channel did carry H.264 frames at 864×1920 and PC taps operated the portrait phone. An eight-second gateway sample saw 140 delivered frames, but a screen with little motion can legitimately emit fewer than 30 frames/s; browser-rendered FPS and end-to-end latency were not measured. Landscape exposed a separate deterministic UI failure: a 2400×1080 phone image was contained inside a fixed portrait viewer and became a narrow strip.

## Confirmed defects and patches in this branch

| Severity | Finding and trigger | Root code path | Patch / verification |
| --- | --- | --- | --- |
| P0 | A failed or stopped mission left Android `DeviceState.controller=HUMAN`, so subsequent Lab missions were rejected. | `OverlayChromeMachine.finishStopped()` paused input even when the terminal state was request-ready; `GatewayV5LabAdapter.start()` correctly rejects human ownership. | Terminal cleanup now releases the temporary stop pause. An explicit owner takeover stays human-owned and remains resumable in the overlay. Regression tests cover stop → next mission and takeover → hand-back. |
| P0 | Merely watching the Glass focus stream silently changed the **gateway** input owner to HUMAN. | The video WebSocket handler assigned `session.input_owner="HUMAN"` when `profile=focus`. | Removed the assignment; a WebSocket regression check asserts watching does not claim control. |
| P1 | Landscape video was tiny inside a portrait-shaped black frame. | Glass `.live-view` hard-coded a 9:19.5 aspect and fixed height while canvas frames changed dimensions. | The viewer now sizes from decoded frame dimensions and expands the landscape column. Glass tests cover orientation changes and normalized coordinate mapping. Physical verification of this new build is still required. |
| P1 | A query such as “Auto-rotate screen setting” returned unrelated Settings controls. | `GatewayObservationAdapter.score()` accepted one matching word from a long query, so “Screen timeout” could be presented as relevant. | Multiword search now requires more than one substantive word to match; a test rejects unrelated rows while keeping the target. This narrows one source of noise; it does not prove the agent can reach an offscreen switch. |

The control system still has **two authorities**: Android `DeviceState.controller` and gateway `DeviceSession.input_owner`. Glass Take/Give changes the gateway flag, while Lab start checks Android. That is a confirmed architectural split from the source and the live badge mismatch; the above patches remove two triggers but do not merge the authorities. The durable fix is one phone-owned control lease with a monotonically increasing epoch, task/session identity, explicit take/yield acknowledgments, and an observed owner value returned to Glass. A stale PC response must never overwrite a newer phone takeover. Browser video subscription must remain read-only. Take/yield must route through Task Kit when a task owns the phone, and approval gates must remain closed across handoffs.

## Mission execution weaknesses exposed by auto-rotate

1. **Poor target discovery.** The `screen_find` matcher was permissive, while the target may have been offscreen. The search patch reduces false candidates. Add a screen-level “not found here” outcome and structured ranking evidence so the model can choose another route instead of treating a generic Settings row as the goal.
2. **Stale targets and ineffective gestures.** The run recorded three scroll errors, two type errors, two tap errors, and a stale swipe ref. Revalidation correctly refused unsafe actions; the recovery policy was weak. On stale-element errors, force a fresh observation and invalidate the old ref before the next action. On two “screen did not visibly change” results, stop repeating that gesture and try a different scroll container or Settings navigation path. Never relax freshness checks to raise the apparent success rate.
3. **Unbounded wandering within the time limit.** Forty-seven turns for a one-switch request is a poor user experience even without a provider failure. Add a progress budget by distinct page/target and tool-error cluster. After a small number of failed route attempts, switch strategy once (direct Settings page → Settings search → visual route), then return an honest failure with the last verified state. Track model tokens, elapsed time, and actionable progress separately.
4. **Settings-specific reachability.** `open_settings(display)` reached Display and touch, but not the switch. A stable semantic settings route should locate the named preference in the current OEM/Android UI, observe checked state, mutate once, and verify the OS value or UI state. This must remain a normal UI action, not a hidden settings-write shortcut that evades user policy.
5. **Result proof.** The Lab correctly used Android's setting value as the verdict. Production success must use a similarly independent after-state check. Tool success, a changed screen, or a model summary is not task completion. Include the exact proof in the user-visible run and distinguish `failed`, `timed out`, `needs owner`, and `infra`.

## Mirror, input, and connection work still required

| Area | Recommended engineering change | How to prove it |
| --- | --- | --- |
| Control authority | Replace mirrored owner flags with a phone-acknowledged, epoch-scoped control lease. Treat reconnect/reload and task completion as reconciliation events. | Take/yield during idle, running, approval gate, lock, disconnect, and two simultaneous browser tabs; assert one owner and no ghost tap. |
| Input coordinates | Bind each click to the **displayed frame** dimensions, crop/letterbox, rotation, and stream epoch; reject clicks on black bars or stale frames. Keep the existing phone-side normalized-to-current-display mapping. | Nine-target grid in portrait/landscape, navigation bars, display cutouts, font/display scaling, and the first click after takeover. Record error in pixels and failed taps. |
| Video pipeline | Measure source capture → gateway delivery → browser decode → paint, not only socket frames. Keep bounded decode queues and prefer dropping stale frames to accumulating lag. Surface actual codec, dimensions, source, FPS, stalls, and fallback mode in diagnostics. | Continuous-motion scene, static scene, rotation, app transitions, 30-minute soak, browser reload and USB reconnect. Report median/p95 latency and stalls per minute. |
| Fallback | The gateway's JPEG degraded focus path is 2 fps; it should be clearly labeled as degraded, automatically recover to H.264, and never be presented as a satisfactory remote desktop. | Force H.264 failure/recovery and confirm visible state, retry backoff, and no permanent low-rate trap. |
| Stop and queue | A stop must be idempotent and leave the targeted task truly terminal. Lab stop should wait for phone acknowledgment and record whether a queued task was promoted. Explicitly define whether user-created queue entries survive a global stop. | Rapid Stop twice, Stop during provider call/approval/reconnect, then new start. Check queue and controller state on the phone, not only the button response. |
| Reconnect | Model USB, ADB authorization, trusted bridge, media, and input as separate health planes; a green USB indicator must not imply live video. Auto-recover with bounded backoff and a clear actionable reason. | Cable removal, ADB server restart, lock/unlock, app process death, accessibility restart, and PC reboot without duplicating a task. |
| Compatibility | Handshake capability and version for phone, gateway, Glass, encoder, and control protocol. Fail closed with an update message when a capability is missing. | Upgrade and rollback matrix across adjacent versions, including retained pairing and old browser tabs. |

## Release gate for the next physical build

These are **proposed acceptance targets**, not results from Alpha 33:

- The eight-mission canary runs end-to-end with zero infrastructure errors; audit every phone-side verdict and the delete-file boundary before the 29-mission baseline.
- No unauthorized consequential action, duplicate action, or false-success verdict in the safety set. A single breach blocks release.
- Repeated common tasks meet a defined success target with confidence intervals and per-app breakdown; report failures honestly. Avoid a universal “works for anyone” claim from one device.
- During an attended 30-minute USB session, video reconnects without manual restart, the browser renders a usable moving screen, portrait/landscape taps hit intended targets, and Stop leaves no active task. Set explicit p95 start/recovery/latency and stall thresholds after baseline measurement rather than tuning to a single trace.
- Run a compatibility matrix across Android 13–latest supported, Pixel/Samsung/other OEMs, screen sizes and densities, gesture/3-button navigation, locked/unlocked and screen-off states, USB reconnects, Wi-Fi fallback, accessibility disruptions, app updates, and low-memory conditions. Include at least one device without optional Google apps.

The connected phone still has the stock Alpha 33 APK; no new APK or Gateway binary was installed during this review. Re-run the physical canary on a versioned build before claiming the handoff or landscape defect fixed in the product.
